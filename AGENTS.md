# AGENTS.md

Инструкции для ИИ-агента, который работает с этим репозиторием. Читай файл целиком перед началом любой задачи.

## О проекте

Веб-панель для стримера на Twitch, который платит деньги за нарезки своих стримов (TikTok, YouTube Shorts, Instagram Reels). Платит за ролики от **2000 просмотров**.

Панель решает две задачи:
- **Нарезчик** добавляет свои аккаунты, подаёт заявки на оплату роликов, общается с модератором в чате заявки, копит баланс и запрашивает вывод.
- **Модератор** видит все заявки в одном месте (а не в Telegram-чате), проверяет их, одобряет или отклоняет, подтверждает аккаунты и выплаты.

Разработчик один, поэтому приоритет: простота, надёжность, минимум лишних зависимостей. Не усложняй архитектуру без необходимости.

## Стек

- Next.js (App Router, `src/`), TypeScript, Tailwind CSS
- PostgreSQL 16 в Docker (`docker-compose.yml`, порт 5433)
- **Prisma 6** (`prisma@6`, `@prisma/client@6`). Генератор `prisma-client-js`. НЕ использовать Prisma 7, не создавать `prisma.config.ts`, не менять `generator` на `prisma-client`.
- Авторизация: Auth.js (`next-auth@beta`), Credentials-провайдер по логину, пароли через `bcryptjs`
- Регистрация закрытая: аккаунты создаёт только модератор на `/moderator/users`; публичной страницы регистрации нет.
- Мутации через Server Actions
- Чат: polling раз в 5 секунд (без WebSocket на старте)
- Уведомления: Telegram-бот
- ОС разработчика: Windows, терминал PowerShell / терминал VS Code

## Структура данных

Схема в `prisma/schema.prisma`. Модели: `User`, `PlatformAccount`, `Submission`, `Message`, `SubmissionReadState`, `WeekClosure`, `WeekResult`, `LedgerEntry`.

- Роли: `CLIPPER` (по умолчанию для новых аккаунтов), `MODERATOR` (выдаётся вручную через Prisma Studio).
- Логин хранится в нижнем регистре после `trim`; при создании допустимы `a-z`, `0-9`, `_`, `.`, `-`, длина 3–32 символа. Пароль — минимум 8 символов и не более 72 байт в UTF-8.
- Отключённые пользователи (`isActive = false`) не могут войти. Каждая защищённая серверная операция проверяет пользователя, активность и роль по базе данных.
- После пяти неверных попыток входа подряд логин блокируется на 10 минут; счётчик хранится в PostgreSQL и сбрасывается после успешного входа.
- Платформы: `TIKTOK`, `YOUTUBE`, `INSTAGRAM`.
- Статусы аккаунта: `PENDING`, `APPROVED`, `REJECTED`.
- Статусы заявки: `PENDING`, `APPROVED`, `REJECTED`, `PAID`.
- Типы записей журнала: `ACCRUAL`, `PAYOUT`, `ADJUSTMENT`.

## Бизнес-правила (строго соблюдать)

### Недельное окно
- Неделя идёт с **понедельника 01:00 до воскресенья 22:00 по московскому времени** (UTC+3, без перехода на летнее время).
- Ролик должен быть **опубликован внутри текущего окна**, и заявка должна быть **отправлена внутри того же окна**.
- Ролик, опубликованный вне окна (например, в воскресенье после 22:00), **не засчитывается вообще** и не переносится на следующую неделю.
- Заявка, отправленная после закрытия окна, отклоняется сервером автоматически.
- Все функции окна принимают `now`; текущий момент сервер получает через `src/lib/now.ts` (`DEV_FAKE_NOW` только вне production). Вся логика недельного окна живёт в `src/lib/week.ts` (`getWindow`). Не дублируй её в других местах.
- В интерфейсе отправки заявки показывать: текущую неделю, обратный отсчёт до закрытия и памятку с этим правилом.

### Заявки
- Подавать можно только с аккаунта, который принадлежит пользователю и имеет статус `APPROVED`.
- Один ролик можно подать только один раз (`videoUrl` уникален).
- Минимальный порог для оплаты: **2000 просмотров**.
- Любая заявка проходит ручную проверку модератора (нарезка с нужного стрима, не украдена, нет накрутки). Автоматически подтягиваются только просмотры и дата публикации.
- В `weekStart` сохраняется начало окна, в которое попал ролик.
- Дату публикации вводят как московское время (UTC+3), переводят в UTC арифметикой; даты в БД хранятся в UTC.
- Каноническая ссылка на ролик строится по ID YouTube/TikTok или shortcode Instagram без параметров. Сервер не делает HTTP-запросов по ссылке пользователя.
- Не более 100 заявок пользователя за неделю (`MAX_SUBMISSIONS_PER_WEEK` в `src/lib/config.ts`, настраивается окружением).
- Модератор вручную проверяет и вводит `views`, при необходимости исправляет `publishedAt`. Просмотры — целое число от 0 до 1 000 000 000; для одобрения нужно не меньше `MIN_VIDEO_VIEWS`.
- При одобрении сумма рассчитывается целыми центами по линейной ставке. Смена статуса и фиксация `views`, `publishedAt`, `amountCents`, `reviewedAt` выполняются атомарно; после одобрения эти значения не меняются.
- Отклонение требует `rejectReason` длиной 3–500 символов. Повторное решение по заявке не перезаписывает итог.
- Отключённый пользователь виден модератору, но решение по его заявке требует явного подтверждения.
- На шаге подачи и модерации заявки записи `LedgerEntry` не создаются.

### Чат внутри заявки
- У каждой заявки своя ветка сообщений (`Message`).
- Читать и писать могут только активный владелец заявки и активный модератор; доступ проверяется на сервере по данным БД. Чужому нарезчику и для несуществующей заявки возвращается одинаковый 404.
- Сообщения только добавляются. Текст обрезается по краям, пустой текст запрещён, не более 2000 символов; более двух переводов строки подряд схлопываются до двух. Текст отображается как обычный экранированный текст.
- Лимит отправки на пользователя: не более 10 сообщений за минуту и 200 за сутки. Проверка счётчиков и создание сообщения выполняются в транзакции с блокировкой строки пользователя `FOR UPDATE`.
- Polling выполняется раз в 5 секунд через `GET /api/submissions/[id]/messages`, с составным курсором `(createdAt, id)`, без кеширования; скрытая вкладка polling приостанавливает.
- Первичная загрузка чата ограничена последними 50 сообщениями. Для списка заявок непрочитанные сообщения считаются одним агрегатным запросом и только для сообщений других участников. `SubmissionReadState` хранит отметку отдельно для каждого пользователя; отметка монотонно обновляется при открытии заявки и видимом polling.
- События подачи, одобрения и отклонения строятся в интерфейсе из полей заявки и не сохраняются в `Message`.

### Выплаты и копилка
- **Все суммы хранятся в центах (`Int`).** Используй константы из `src/lib/config.ts`, не хардкодь ставки и пороги: `RATE_CENTS_PER_1000` (200), `MIN_VIDEO_VIEWS` (2000), `MIN_WEEK_VIEWS` (5000), `PAYOUT_THRESHOLD_CENTS` (3000). Значения читаются из одноимённых переменных окружения с указанными значениями по умолчанию.
- Ставка линейная: `amountCents = floor(views * RATE_CENTS_PER_1000 / 1000)`. При ставке 200 ролик с 2000 просмотрами даёт 400 центов ($4). Ролик засчитывается от 2000 просмотров.
- Итог недели нарезчика — сумма `amountCents` его одобренных роликов с одинаковым `weekStart`.
- `LedgerEntry` хранит только деньги, доступные к выводу; баланс равен сумме `amountCents` пользователя. Копилка в журнал не попадает.
- Неделя меньше 5000 просмотров (меньше суммы `MIN_WEEK_VIEWS` по ставке, сейчас 1000 центов) не начисляется и не добирает копилку.
- Итог от минимального недельного порога до суммы меньше `PAYOUT_THRESHOLD_CENTS` становится копилкой ровно на следующую закрытую неделю. Если копилка плюс итог следующей недели достигают порога, вся сумма становится доступной к выводу. Иначе старая копилка сгорает, а новый итог недели (если он достиг минимума) становится новой копилкой.
- `carryInCents` берётся только из `WeekResult.carryOutCents` непосредственно предыдущей закрытой недели. Сгоревшая сумма хранится в `WeekResult.expiredCents`; записей `EXPIRY` в журнале нет.
- Модератор вручную закрывает недели по порядку после окончания окна и обработки всех заявок `PENDING`. До закрытия показывается предпросмотр; закрытие атомарно, идемпотентно и пересчитывает данные на сервере. Пустые недели после первой недели с заявками тоже закрываются, чтобы сохранить цепочку.
- Для недельных `ACCRUAL` обязателен `weekStart`; PostgreSQL защищает уникальность пары `(userId, weekStart)` частичным уникальным индексом. `submissionId` остаётся уникальным.
- `WeekResult` хранит только неотрицательные суммы; PostgreSQL проверяет это `CHECK`-ограничением. На `weekStart` есть индекс для чтения истории.
- `WeekResult`, `WeekClosure` и `LedgerEntry` неизменяемы и не удаляются. Начисление за неделю и результаты создаются в одной транзакции при закрытии. Просмотры и сумма заявки фиксируются при одобрении; после закрытия недели принимать решения по её заявкам нельзя.
- Способы вывода: криптовалюта (`wallet`) или скины CS (`steamTradeUrl`). Выплату вручную подтверждает модератор; запись `PAYOUT` имеет отрицательную сумму.

### Аккаунты платформ
- Пользователь добавляет аккаунт (платформа + ссылка), статус `PENDING`.
- Модератор одобряет или отклоняет. Пока аккаунт не одобрен, подавать с него ролики нельзя.
- Пара (`platform`, `url`) уникальна.
- Добавлять аккаунты можно только во вторник с 00:00 до 22:00 по МСК (UTC+3, без летнего времени). Проверяй окно на сервере в Server Action; его отдельная логика находится в `src/lib/account-window.ts`.
- У одного пользователя может быть не более трёх аккаунтов каждой платформы со статусом `PENDING` или `APPROVED`. Аккаунты `REJECTED` в лимит не входят. Проверка лимита и создание или повторная подача должны быть атомарны; повторная подача собственного отклонённого аккаунта возвращает существующую запись в `PENDING`.
- Принимать только ссылки на профили и каналы: TikTok `tiktok.com/@user`, YouTube `youtube.com/@handle` или `youtube.com/channel/ID`, Instagram `instagram.com/user`. Ссылки на видео и сокращённые домены отклоняются. Убирай `www.`, query-параметры, hash и завершающие `/`, имя пользователя нормализуй в нижний регистр.
- В интерфейсах, где нужен идентификатор пользователя, показывай `login`, не внутренний `id`.

## Безопасность (обязательно)

- **Все проверки и расчёты только на сервере.** Ничего не доверять данным из браузера: сумма, статус, `userId`, `publishedAt`, `weekStart` на клиент не отдаются как редактируемые поля.
- В каждом Server Action и API-обработчике сначала проверяй сессию и роль. Страницы `/moderator/*` доступны только `MODERATOR`, и это проверяется и в `middleware.ts`, и внутри самих действий.
- Пользователь видит и меняет только свои данные (аккаунты, заявки, сообщения).
- Входные данные валидируй (рекомендуется `zod`).
- Пароли только хешированные (`bcryptjs`). Никогда не логируй пароли, токены и ключи.
- Не раскрывай чужие данные в ответах и сообщениях об ошибках.
